# 実装計画

> 2026-09-13 に design-doc 8 章の制御モデル（coordinator があるべき状態を作り、proxy がそれを実現する）に合わせて改訂した。旧方式（proxy が予算をリースし、coordinator は帳簿に徹する）の記述は残していない。

M1 で単体の予算スケジューラを作り、M2 でそれを分散させる。**M1 の完了時点で、既存プーラーが解いていない 3 問題のうち 2 つが解けている状態**にする。各ステップは 1 つの小さな CL に対応し、テストを先に書く。

本書では契約も決定も**名前で呼ぶ**。読むときに記号を引き直さなくて済むようにするためである。

## 用語

design-doc 9 章の用語集に揃える。ここには実装で頻出するものだけを再掲する。

| 用語 | 意味 |
|---|---|
| クライアント接続 | アプリケーションから proxy への TCP 接続 1 本 |
| DB 接続 | proxy から PostgreSQL への TCP 接続 1 本。契約では「サーバー接続」と呼んでいるもの |
| 割り当て | ある DB 接続が、あるクライアント接続に貸し出されている状態。トランザクションモードではトランザクション単位で続く |
| インスタンス | 1 つの PostgreSQL サーバー（`host:port`）。総予算を持つ単位であり、配分の計算が閉じる単位 |
| テナント | `user × database` の組。配分と隔離の単位。接続してよいインスタンスの集合を持つ |
| 接続枠 | DB 接続を 1 本張ってよいという権利。**払い出しの単位**であり、クエリでもトランザクションでもない |
| 割当表（あるべき状態） | 「インスタンス × テナント × proxy → 接続枠の本数」の表。coordinator が計算し、Raft で複製する正典 |
| 総予算 | 1 つのインスタンスに対して本システムが張ってよい接続数の上限。**設定に書かず、システムが `max_connections` と他者の接続の観測から導出する** |
| 需要 | proxy があるテナントについて必要としている接続数。待機キュー長と使用中の接続数から算出し、定期の報告に載せる |
| 要求 | proxy が coordinator に接続枠を求めること。需要の変化時にだけ発生する |
| 払い出し | coordinator が proxy に接続枠を与えること。期限があり、更新できなければ失効する |
| 回収 | coordinator が proxy に接続枠を手放すよう指示すること。proxy はアイドルな接続から閉じ、実行中のトランザクションは中断しない |
| 調停 | 未払い出しの余剰が尽きているときに、あるべき状態を計算し直し、回収と払い出しを組み合わせて要求を満たすこと。他の proxy から能動的に回収する部分をプリエンプションと呼ぶ |
| 収束 | proxy が実接続を払い出しに一致させること。増えた分は張り、減った分は閉じる |
| 自己フェンス | 払い出しを更新できなくなった proxy が、指示を待たずに自ら全接続を閉じること |
| proxy | ワイヤプロトコルを話す実体。クライアント接続を受け、DB 接続を保持する。**配分の判断を持たない** |
| coordinator | あるべき状態を計算し、Raft で複製し、proxy に配る役割。クライアント接続も DB 接続も持たない |

## 1. 全体構成

Cargo workspace を 5 つの crate に分け、M1 では上 4 つを作る。**パッケージ名にはすべて `pgsteward-` を付ける。** `core` は Rust の組み込み crate `core` と衝突するので、パッケージ名は `pgsteward-core`（ディレクトリは `crates/core`）とする。他も同様に `pgsteward-protocol`、`pgsteward-sched`、`pgsteward-node`、`pgsteward-coordinator` である。以下の表と本文では短く `protocol` / `sched` / `core` / `node` / `coordinator` と呼ぶ。

| crate | 責務 | 依存 | M |
|---|---|---|---|
| `protocol` | ワイヤプロトコル v3 のフレーミング、メッセージ型、ReadyForQuery を監視する状態機械。入出力を持たない純粋な層 | `bytes`, `postgres-protocol` | 1 |
| `sched` | **配分アルゴリズム。** 総予算と需要と現在の払い出し量から、あるべき状態（目標の払い出し量）を出す純粋関数のトレイトと、既定実装の重み付き max-min fair。入出力も時間も持たない | なし | 1 |
| `core` | クライアントセッション、DB 接続、プール、待機キュー、リセット、認証、キャンセル、**割当表と配分器と制御ループを 1 プロセス内に持つ縮退形の coordinator（自分自身に払い出す）**。読み書きの抽象に加えて**時計とタスク生成も抽象化**（`rt` モジュール） | protocol, sched, `tokio`, `tokio-rustls`, `scram-rs` | 1 |
| `node` | バイナリ。ノードローカル設定とクラスタ設定の初期値の読み込み、**役割の切り替え**、リスナー、管理コンソール、メトリクス、シグナル処理 | core, `prometheus-client`, `clap` | 1 |
| `coordinator` | **Raft 割当表、要求の受付と払い出し、需要報告の集約、調停と回収（プリエンプション）、失効、自己フェンスの相手方。** coordinator 役割の実体 | core, sched, `openraft` | 2 |

### 1.1 M1 と M2 の境界

この計画の要は、**M1 で作る proxy 側が「払い出しがどこから来たか」を知らない**ことにある。design-doc 8.2 のとおり proxy はあるべき状態を持たず、「今払い出されている枠」を受け取り、「実接続と需要」を報告するだけである。proxy 側のプールが見るのは、その 2 方向のチャネルだけにする。

```
                  core::Pool（proxy 側）
                        │
              trait GrantChannel
        subscribe_grants() / report(demand, actual)
                   ╱            ╲
    InProcessCoordinator（M1）   ClusterCoordinator（M2）
   割当表・配分器・制御ループを   同じ割当表と制御ループを
   同一プロセス内に持ち、        coordinator crate に置き、
   自分自身に払い出す。          Raft で複製して通信で配る。
   要求も払い出しも関数呼び出し   proxy 側は無変更
```

**M1 は新しい制御モデルの縮退形である**（design-doc 13.1）。1 プロセスの中に割当表と配分器と制御ループを持ち、自分自身に払い出す。要求も払い出しも回収も関数呼び出しになるだけで、**design-doc 8.2 の役割の境界はこの時点で引いておく**。境界が引けていれば、M2 で加わるのは通信と合意だけになる。逆に proxy 側のプールに「枠を増やす」「枠を手放す」の判断を持たせてしまうと、分散化のときに書き直しになる。

**配分アルゴリズムそのものは両方で共有される。** M1 は 1 プロセス内の需要だけを入力に回し、M2 は全 proxy の需要を集めて coordinator で回す。入出力の型が同じ（インスタンスごとに、テナント×proxy の最低保証・上限・重み・需要・現在の払い出し量 → 目標の払い出し量）なので、**M1 で書いたプロパティテストが M2 でもそのまま効く**。これが配分器を独立した crate に切り出した理由である（「配分アルゴリズムを純粋関数にする決定」）。

**時間と入出力の抽象化。** 「決定的シミュレーションとモデル検査で正しさを示す決定」により、`std::time::Instant` と `tokio::spawn` と `tokio::net` を直接呼ばない。基盤は**自前の `rt` トレイト**である — `Clock`（現在時刻と `sleep`）、`Spawner`（タスク生成）、`Net`（listen / connect / accept）の 3 つを `core::rt` に閉じ込め、**本番では tokio 実装**を、**`tests/sim` では turmoil を裏に使う実装**を差す。madsim のように tokio を丸ごと差し替える方式は採らない。呼び出し側は `rt` 越しにしか時計もタスクもネットワークも触れない形にして、素朴に書けなくなる範囲を狭める。**これは M1-01 で入れる。** 後から入れることは全入出力の書き換えを意味する。

**設定の 2 層。** design-doc 14.1 のとおり、設定はノードローカル設定（各ノードの TOML。役割、リスナー、coordinator の入口、受け入れ上限、TLS、DB の認証情報）とクラスタ設定（インスタンスの一覧とテナントの `min` / `max` / `weight`。正典は割当表で、TOML は coordinator が空の状態から初期化するときの初期値としてだけ読む）に分かれる。**総予算はどちらにも書かない。** M1 では 1 プロセスが両方を読み、縮退形の coordinator が初期化する。

**ライブラリの使い分け。** DB 側の認証とバックエンドメッセージの解析は `postgres-protocol`。クライアント側の SCRAM サーバー実装は `scram-rs` を評価し、合わなければ RFC 5802 / 7677 に沿って自前で書く。フレーミングは数十行なので自前。`pgwire` は DB サーバーを実装するための枠組みでプロキシには重いので使わない。Raft は `openraft` を第一候補とし、M2-02 で `raft-rs` と比較する。

```
workspace/
├── Cargo.toml
├── crates/
│   ├── protocol/     framing, messages, ready_for_query FSM
```

## 2. テスト戦略

「テストを書く → 失敗を確認 → コミット → 実装 → 通過」の順。テスト名には契約の識別子を含める。

| 階層 | 場所 | 内容 |
|---|---|---|
| 単体 | crate 内 | フレーミング、状態機械、プールの状態遷移。偽の入出力で DB なしに走る |
| プロパティ | `sched` / proptest | 配分器が満たすべき 5 つの性質（総和・最低保証・上限・決定性・単調性）をランダム入力で確認。**トレイトの契約なので実装が増えても同じテストが効く** |
| 統合 | `tests/integration` | Docker 上の実 PostgreSQL 16。単一ノードの契約の大半 |
| シミュレーション | `tests/sim` | 時計・スケジューリング・ネットワークを疑似乱数で制御し、シード値で再現。**並行性と分断はここで潰す** |
| 適合・ベンチ | `bench/`, `tests/conformance` | pgbench、asyncpg 風の extended query 連打、COPY |

**接続上限の検証。** 統合テストとカオステストは実行中ずっと `pg_stat_activity` をポーリングし、`application_name` で本システム由来の接続を数え、**インスタンスごとの総予算（導出値）**を一度でも超えたら失敗にする。シミュレーションでは実 DB がないので、代わりに**偽 PostgreSQL が受け入れた接続数**を同じ判定にかける。両方を `tests/harness` の共通のアサーションとして M1-01 で作る。あわせて design-doc 8.4 の性質 2「proxy の実接続数 ≤ その proxy への払い出し」も同じハーネスで常時検査する — 上限の超過より先に、proxy 単体で検知できるからである。

**決定的シミュレーションの使い方。** CI では固定シード集合（回帰）とランダムシード（探索）の両方を回す。失敗したシードは回帰集合に追加する。**失敗報告は必ずシード値を伴う**ので再現に手間がかからない。docker compose のカオステストは、シミュレーションが実環境と乖離していないかの確認用として夜間に回す。

**状態隔離の検証。** 「汚した DB 接続を返し、次のクライアントから見えないこと」を同じ形で確かめる。`SET`、`PREPARE`、`CREATE TEMP TABLE`、`pg_advisory_lock` の 4 パターンを 1 つのパラメタライズドテストにする。

**CI。** `cargo fmt --check` → `clippy -D warnings` → `cargo deny` → `cargo audit` → 単体 → プロパティ → シミュレーション → 統合。シミュレーションは DB が要らないので統合より前に置き、速く失敗させる。

## 3. マイルストーン 1: 単体の予算スケジューラ

**完了条件**: 1 台で単一ノードの契約と予算スケジューラの契約が通り、pgbench で PgBouncer と同等以上のスループットが出る。加えて**テナント 30,000 件を総予算 100 で捌け、3 テナントが競合しても飢餓が起きない**。

## 4. マイルストーン 2: 分散層

**完了条件**: coordinator 3 台 + proxy 3 台で、どの proxy に繋いでも同じサービスを受けられ、`kill -9`・分断・時計ずれを注入した決定的シミュレーションで DB 接続数が一度も総予算を超えず、再配分の収束時間・復旧時間・接続チャーンの目標値を実測で確定させる。

配置方式の比較は**「分割配置と予算リースの決定」**から**「配分を誰が決めるか」（design-doc 20.2）**に移した。本書は決定済みの方式を実装する手順だけを扱う。

### 4.1 払い出しの安全性

Raft は「誰が何本持つべきか」の割当表であり、**それだけでは足りない** — Raft のクォーラムと対象 PostgreSQL の故障ドメインは一致しないので、自己フェンスと DB 側の保険を重ねる（「自己フェンスの決定」）。design-doc 8.4 の 2 つのローカルな性質（払い出しの総和 ≤ 総予算、実接続 ≤ 払い出し）をつなぐ過渡状態を、次の規則で塞ぐ。

1. **要求と払い出し。** proxy は需要が変化したときだけ coordinator に要求する。枯渇したときは定期の報告を待たずに即時要求を上げる。coordinator は調停周期で全 proxy の需要から配分器であるべき状態を計算し、現在の割当表との差分を 1 つのログエントリにまとめて Raft にコミットしてから、期限つきで払い出す。値には proxy の識別子と Raft のログインデックス（フェンシングトークン）を入れる。**割当表の状態機械は「インスタンスごとに払い出しの総和 ≤ 総予算」を事前条件として検査し、破るエントリはコミットしない**
2. **更新と需要報告。** proxy は期限の 3 分の 1 の間隔で払い出しを更新し、あわせて需要と実接続数を報告する。経過時間は**単調時計**で測る。**proxy は自分の判断で枠を増やさず、減らしもしない** — 需要が消えたことを報告するだけで、割当表から外すのは coordinator である
3. **自己フェンス。** 経過時間が「期限 − 余裕」を超えたら、新規の割り当てをやめ、割り当て中の DB 接続にキャンセルを送り、すべて閉じる。**余裕**は「DB 接続を全部閉じるのにかかる時間 + 時計ずれの許容」以上に取る。proxy の単独判断で動くのはここだけで、向きは減らす方向に限られる
4. **失効と再配分。** coordinator が失効と見なすのは最後の更新から期限が過ぎたとき。規則 3 により**旧保有者の自己フェンスは常にそれより前に終わっている**。失効した枠は割当表から外し、次の調停で要求のある proxy へ配り直す
5. **調停の順序。** 接続枠を proxy A から proxy B へ動かすとき、coordinator は A に回収を指示し、**A の回収完了報告が Raft にコミットされるより前に、その分を B へ払い出してはならない**。この順序だけが移動中の接続上限を守っている。A はアイドルな接続から閉じ、実行中のトランザクションは終わってから閉じる
6. **DB 側の保険。** クラッシュして自己フェンスできない場合に備え、`tcp_keepalives_idle` と `tcp_user_timeout` を払い出しの期限より短く設定し、**起動時に `SHOW` で検証して満たさなければ起動を拒否する**（rev.1 では警告だったが拒否に格上げ）

**証明の外で仮定していること**は design-doc 8.4 の 3 つ（単調時計が単調であること、余裕が十分に大きいこと、DB 側のタイムアウトが実際に効くこと）で、**分断から復帰した proxy の再同期**は未解決のまま残っている（design-doc 19 章）。この 4 つを M2-09 のモデル検査で最初に当てる。

**受け入れる代償**: 分断された proxy は「自分が正しいかもしれない」場合でもサービスを止める。そのテナントは最大「期限 + 再取得時間」の間、その proxy 上で利用できない。加えて coordinator 群が落ちると需要の増加に一切応えられない（既存の払い出しは期限まで有効）。
